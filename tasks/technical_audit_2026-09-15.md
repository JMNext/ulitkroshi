## 2. Детальный аудит ожиданий Заказчика

### 2.1. Ожидание 1: «Админка хоть какая-то»
* **Фактическое состояние:** **Полностью отсутствует**.
* **Анализ кодовой базы:**
  * В коде фронтенда нет ни одного экрана, модального окна или маршрута для администратора (поиск по кодовой базе находит упоминание `admin` только в проверке занятости никнейма в моках).
  * В бэкенде отсутствуют эндпоинты для управления пользователями, просмотра статистики, генерации кодов, блокировок или настройки игрового баланса.
  * Ролевая модель не задействована (в БД есть поле `roles TEXT[] DEFAULT '{user}'`, но проверок прав и разделения ролей в коде нет).

### 2.2. Ожидание 2: «Выбор еды (4 варианта, активация по кодам)»
* **Фактическое состояние:** **Сверстан визуальный интерфейс, логика кодов отсутствует**.
* **Анализ кодовой базы:**
  * **Визуальная часть:** Реализован компонент `FoodPanel.tsx`, открывающий панель с 4 слотами (`fruit_01`, `fruit_02`, `fruit_03`, `fruit_04`) с отображением количества, кулдаунов и анимацией перетаскивания еды на питомца (`startFeedingDrag.ts`).
  * **Логика активации по кодам:** В коде **не предусмотрена**. Еда пополняется только через внутриигровой магазин (`ShopModal.tsx`) за виртуальные монеты.
  * **Сохранение состояния:** Количество еды и кулдауны хранятся исключительно в оперативной памяти Zustand (`usePetStore.ts`). При обновлении страницы (F5) весь инвентарь еды сбрасывается к нулю. В БД нет таблицы инвентаря.

### 2.3. Ожидание 3: «Ввод / сканирование кодов»
* **Фактическое состояние:** **Фронтенд-заглушка без серверной валидации**.
* **Анализ кодовой базы:**
  * **Визуальная часть:** Разработан удобный интерфейс `AddPetScannerModal.tsx` с переключением между сканированием через камеру (на базе `html5-qrcode`) и ручным вводом цифрового/текстового кода.
  * **Логика валидации:** Полностью фиктивная, работает на стороне клиента по формуле:
    ```typescript
    addPetByCode: (code) => {
      const cleanCode = code.trim();
      if (!cleanCode) return false;
      const parsed = parseInt(cleanCode.replace(/\D/g, ""), 10);
      usePetStore.getState().unlockPet(!isNaN(parsed) ? parsed % 20 : (cleanCode.length % 19) + 1);
      return true;
    }
    ```
  * Любой введенный текст или QR-код всегда считается «успешным» и разблокирует питомца по остатку от деления.
  * **Бэкенд:** На сервере **нет таблицы кодов**, нет проверки их подлинности, срока действия, привязки к наградам (еда / питомцы / монеты) и защиты от повторного использования.

## 4. Анализ реализации Бэкенда и готовности к Клиент-Серверному режиму

### 4.1. Что сделано в бэкенде:
Разработчики отказались от архитектуры C# .NET 10 и создали компактный TypeScript/Express бэкенд (`backend/`):
* **`backend/index.ts`** — точка входа Express с поддержкой CORS и JSON-парсинга.
* **`backend/db.ts`** — пул соединений PostgreSQL (`pg.Pool`) и автосоздание таблицы `users`.
* **`backend/auth.router.ts` & `auth.service.ts`** — регистрация, авторизация по телефону, отправка SMS через сервис SMS.ru, фруктовая капча, JWT токены (`accessToken` / `refreshToken`).
* **`backend/game.router.ts` & `game.service.ts`** — расчет естественного убывания показателей питомца (сытость/счастье по времени через формулы в SQL), эндпоинт кормления `/game/feed`, начисление/списание монет с защитой от частого кликанья (Rate Limit 5 сек).

### 4.2. Архитектурные ограничения и блокеры для Prod/MVP:
1. **Отсутствие доменных сущностей в БД:**
   * В базе данных создается **только одна плоская таблица `users`**.
   * Нет таблиц для:
     * Инвентаря еды и предметов пользователя;
     * Базы промокодов и QR-кодов (активирован / кем / когда / тип награды);
     * Лога транзакций и истории начислений;
     * Прогресса и рекордов мини-игр.
2. **Сессии в оперативной памяти (In-Memory Sessions):**
   * Сессии подтверждения SMS хранятся в JavaScript-коллекции `phoneSessions = new Map()`. При любом перезапуске сервера (деплой, сбой, перезагрузка контейнера) все незавершенные сессии пользователей стираются.
3. **Отсутствие связки с фронтендом:**
   * Эндпоинты фронтенда и бэкенда не синхронизированы по контрактам инвентаря и кодов.
   * Отсутствует механизм проксирования API в продакшне (настройки Nginx / Traefik / SSL не описаны, старые Ansible-скрипты удалены).

## 6. Рекомендации и план первоочередных работ для сдачи MVP

Для доведения проекта до соответствия заявленным требованиям MVP Заказчика необходимо:

1. **Серверная система кодов и инвентаря (Блокер MVP №2 и №3):**
   * Создать в БД таблицы: `promo_codes` (код, тип награды: `food`/`pet`/`coins`, количество, `is_used`, `used_by_user_id`) и `user_inventory` (user_id, item_id, count).
   * Реализовать эндпоинт `POST /game/codes/redeem` с проверкой подлинности кода и начислением соответствующей еды/питомца.
   * Привязать модалку сканера `AddPetScannerModal` к реальному эндпоинту вместо математического мока.
   * Привязать отображение доступной еды в `FoodPanel` к инвентарю пользователя из БД.

2. **Подключение клиент-серверного режима (Блокер Демо):**
   * Заменить `isMock = true` на конфигурацию через переменные окружения (`import.meta.env.VITE_API_URL`).
   * Настроить продакшн-деплой бэкенда на сервер с подключением к PostgreSQL и публичному домену API с SSL.

3. **Базовая панель администратора (Блокер MVP №1):**
   * Реализовать минимальную админ-страницу (на Ant Design, который уже установлен в проекте):
     * Просмотр списка зарегистрированных пользователей и их питомцев;
     * Генератор промокодов/QR-кодов с выбором типа награды (еда 4 видов, монеты, питомцы);
     * Просмотр статуса активации кодов.
